# Design: 凭据代理与受限令牌

## Context

执行主机当前通过 `dsh-superagent` 写入的 `worker-gitconfig` 调用 `gh-agent auth git-credential`，后者从 `~/.config/gh-agent/hosts.yml` 读取 `gho_…` 真 token。这条路径上，真 token 同时出现在：

- 执行主机的磁盘上
- 任何被执行命令的环境可达范围内
- `gh` 进程的命令行之外（幸好不在 argv 里）

DSH 的 `ctx.shell` 已经被 dsh-remote-exec 接管，所以执行主机上的每条命令都可控。本设计利用这一点，把出网凭据收进云端。

## Goals

- 执行主机上不存在任何长期有效的提供商凭据。
- 凭据的可用范围与工单绑定：一个工的令牌不能推另一个工的仓库或分支。
- 被拒绝的请求必须可追溯，且拒绝原因可读。
- 真 token 永不进入模型上下文。

## Non-goals

- 不做通用 OAuth 代理；只服务 git 的 https 推送与拉取。
- 不做令牌的多租户隔离；本变更是单操作者部署。
- 不改动 GitHub 侧的权限模型。

## Trust boundary

```
┌─ 高信任区 ────────────────────────┐
│  Agent Loop 进程                   │
│  ├─ 真 token（内存中，不落盘）      │
│  ├─ 代理校验逻辑                   │
│  └─ 审计日志                       │
└───────────────┬───────────────────┘
                │ 受限令牌（JWT，有效期 1 小时）
                │ 真 token 永不下行
┌───────────────▼───────────────────┐
│  执行主机                          │
│  └─ 只知道：这张工单能推哪个分支     │
└───────────────────────────────────┘
```

**边界假设**：云端可信，端侧不可信。这与 Grok Bot 相反（它假设端侧就是用户本人），符合 super-agent 的场景：端侧是操作者的开发机，但上面运行着可能被注入的命令。

## Token claim 结构

```json
{
  "iss": "dsh-remote-exec",
  "sub": "ticket:63a457eddf50",
  "aud": "git-proxy",
  "repo": "yeffky/camera-agent",
  "refs": ["refs/heads/agent/build-apk-*"],
  "ops": ["fetch", "push"],
  "iat": 1793696400,
  "exp": 1793700000,
  "jti": "8f3c…"
}
```

签发方是 Agent Loop。签名密钥在云端内存中生成，进程重启即失效（不落盘，重启后旧令牌全部作废，符合「脑不可用则手不行动」）。

## 代理校验顺序

校验在**任何**副作用之前完成，且顺序固定以便审计可复现：

1. `exp` 未过期
2. 签名有效（防伪造）
3. `aud` 匹配
4. `repo` 等于请求目标仓库
5. `ops` 包含请求操作（fetch / push）
6. 请求的 ref 匹配 `refs` 中任一模式
7. 仅当以上全部通过，才注入真 token 转发

任一步失败 → 拒绝 + 审计(claim 名 + 请求摘要)，**不是**通用 500。

## 为什么用受限令牌而不是「代理直接认执行主机」

如果代理只验证「这是本机的 daemon」，那么任何能在执行主机上跑命令的东西都能推送。受限令牌把权限绑定到**工单**，使一个被注入的命令最多能推它自己那个工单的分支。

## 环境脱敏

执行主机上 `worker-gitconfig` 改为：

```gitconfig
[credential]
	helper =
[credential "https://git-proxy.internal"]
	helper = "!f() { echo username=ticket; echo password=$REMOTE_EXEC_TOKEN; }; f"
[url "https://git-proxy.internal/"]
	insteadOf = https://github.com/
```

`REMOTE_EXEC_TOKEN` 是受限令牌。它出现在执行主机环境里**是可以接受的**，因为它本身就设计为可暴露：过期、限仓库、限分支。

## 失败行为

| 情况 | 行为 |
| --- | --- |
| 令牌过期 | 拒绝，提示重新签发；已运行的命令不受影响 |
| 代理不可达 | git 报连接失败；命令失败，不重试 |
| 云端重启 | 签名密钥失效，执行主机上的旧令牌全部失效；需要重新签发 |
| 代理校验失败 | 拒绝并审计；命令收到明确错误 |

**不自动重新签发**：签发发生在创建工单时，令牌过期意味着工单运行过久，应该由人决定是否续期。

## 脱敏规则

审计与工具结果在离开高信任区前，按以下模式替换为 `[redacted:<kind>]`：

- `gh[pousr]_[A-Za-z0-9]{20,}`
- `github_pat_[A-Za-z0-9_]{20,}`
- `eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}`（JWT 形态，避免受限令牌被当凭据记录）
- 配置中显式登记的字符串

## 开放问题

- **代理如何防止令牌被重放？** 目前靠短有效期。若要更强，可加 `jti` 一次性使用记录。
- **执行主机上是否还需要 `gh`？** GitHub API 调用也需要凭据。本变更先覆盖 git；`gh api` 走代理是下一步。
- **跨仓库工单**：当前一个工单一个仓库，若将来一个工单涉及多个仓库，`repo` claim 需改为列表。
